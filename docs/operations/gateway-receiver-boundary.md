# Gateway receiver binding

An encrypted provider binding and native admission policies fence the application
Gateway. Every TLS chain accepts only the load balancer's private address. The
forwarding protocol does not change: provider and receiver PROXY settings remain
explicitly disabled, and turning them on is a later reviewed activation.

The eventual fence uses Envoy's `direct_source_prefix_ranges` on every TLS
filter chain. This matches the physical connection peer independently of any
client address claimed by a PROXY header. Cilium's ingress identity alone does
not establish that boundary: the pinned listener processes PROXY metadata before
resolving the source identity used for ingress policy. Adding an egress policy
alone does not close the path that is redirected to the gateway first.

The mutating and validating policies target only the declared application
Gateway's generated CiliumEnvoyConfig. They preserve its existing plain HTTP
chain and other resources, require every TLS chain to use the same exact host
prefix, and reject fallback chains, alternate matchers and protobuf field aliases
that could evade that check. No global webhook selector is widened. The
`components/physical-peer-fence` component binds them, and the Hetzner Cilium
layer selects it.

## Prepare or replace the binding

From an isolated checkout of the reviewed Platform revision, run:

```sh
go run ./scripts/gateway-receiver-binding
```

The producer uses the scoped production context, checks the Service's Gateway
owner and current accepted/programmed controller state, and requires the explicit
disabled provider baseline. It admits exactly one private IPv4 address and emits
only its host prefix. It refuses unexpected ports, another provider path,
ambiguous addresses, duplicate JSON keys, or changing identities.

SOPS uses the repository's production creation rule and existing public
recipient. No private recovery key is read. Plain input stays in a private
temporary workspace; the checkout receives the validated encrypted Secret only
after a second matching metadata read. The producer never applies a resource or
changes a provider setting. The destination is created exclusively. To preserve
the existing file while preparing a replacement after infrastructure recovery:

```sh
go run ./scripts/gateway-receiver-binding --output /tmp/gateway-receiver-candidate.enc.yaml
```

Review that encrypted replacement through the normal signed PR workflow. An
operator recovering through the independent production API may explicitly select
`--context admin@prod`; the producer never escalates a failed scoped read.
Restore the disabled provider baseline before rebinding. This bootstrap binding
and its recovery recipient remain separate from operational keys in OpenBao.
The encrypted Secret belongs to `clusters/prod/bootstrap`, whose Flux
Kustomization declares SOPS decryption before infrastructure reconciliation.
The root reconciliation does not decrypt secrets and must not own this file.

## Protected deployment and restoration

The shared protected deployment verifies the current encrypted binding against
actual Service and Gateway identities. It requires both unbound policy specs to
match reviewed source and the validating policy's current generation to have
completed type checking without warnings.

Before restoring disabled state, the helper checks the generated listener and
both bindings. An active PROXY listener, unknown owner, changed peer, foreign
binding, or ambiguous configuration refuses every planned write. The helper
removes only its exact bindings with observed UID and resource-version deletion
preconditions, then conditionally removes only its owned peer fields and marker.
It preserves all other controller configuration and metadata. Readback resolves
lost acknowledgements; a replacement or uncertain outcome never reports success.
This mutation runs only in the reviewed protected deployment, never directly from
an agent session.

Both deployment steps follow what the checked-out Hetzner infrastructure layer
renders. While it renders neither binding, they restore and verify the disabled
baseline. When it renders both, from any level of the overlay, `restore-disabled` writes nothing
and reports `GATEWAY_RECEIVER_DISABLED=NOT-APPLICABLE fence=selected`, and `verify`
requires both reviewed bindings, the ownership marker and the exact peer on every
TLS chain. A revision that goes back to unselected, including main's recovery after
a failed activation, removes the fence as before. A failed render, missing
policies or a partial or foreign binding fails without a write.

Admission applies only when the generated listener is written, and the controller
does not rewrite an unchanged listener. So between those two steps, `apply-selected`
waits a bounded time for the reviewed policies and bindings, which arrive with the
later `infrastructure` Flux layer, then writes only the ownership marker, conditional on the observed UID
and resource version. Admission installs the fence on that write, including after a
listener lost it. It writes nothing when the fence is already active or the source
leaves it unselected, and refuses a foreign owner, a different peer or an active
PROXY listener. Every step still refuses an active PROXY listener, so turning the
transport on needs its own change to this helper.

## Recovery while selected

If the fence itself refuses public traffic, revert the selection: the deployment on
the reverted source removes the bindings and the fields it installed.

The bound peer belongs to one load balancer. A replacement that keeps the Gateway
but changes the private address leaves a fence with the old peer, which refuses
every public TLS route and fails `apply-selected`. Revert the selection, deploy,
prepare the replacement binding, then select it again. A rebuilt cluster with a stale
binding has the same problem, so unselect the fence before rebinding it.

The following read-only check requires what the source selects, and the generated
listener free of PROXY filters:

```sh
go run ./scripts/gateway-receiver-binding verify --context admin@prod
```

It probes Homepage and OpenBao through the provider's actual public endpoint with
normal hostname and TLS verification, bypassing edge caches, and repeats with
unchanged source identities. `GATEWAY_RECEIVER_SOURCE=VERIFIED fence_selected=true`
establishes the fence on every TLS chain and positive public paths. It does not
prove that another peer is refused, original-client attribution, Email
administration, or protocol activation.

Before turning the transport on, #5448 still requires native denied peer probes,
forged PROXY metadata rejection, controller revision stability, the real Email
path, authenticated administration and observed recovery. Preserve all stored
access rules throughout that work.
